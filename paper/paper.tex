\section{Introduction}

Collaborative text-editing algorithms allow multiple users to edit the same text document concurrently. These algorithms are used in popular
software such as Google Docs and Overleaf. There have been many of these algorithms suggested, in academia, industry and as
open source implementations. Many of these algorithms are published without proof of the properties they satisfy, or with
proofs that were later found to be incorrect. Existing work has found bugs in many of these algorithms, so there is reason to believe
other algorithms may also not work. 

This paper aims to collate the existing work on collaborative text-editing algorithms, to determine which algorithms satisfy which
properties, and to determine which published algorithms work. Many published algorithms have no publically available implementation, so we provide
an implementation for each of the algorithms. The only way to be certain about an algorithm's properties is to write a formal mechanised proof. This is difficult, time-consuming, and only checks an idealised model of the algorithm, not an actual implementation. We help with these
problems by providing a model-checker specialised for the task of testing properties of collaborative text-editing algorithms. This model-checker has been used to find the properties
of each of our implementations, and would also be useful for verifying any future algorithms. This model-checker also provides a more factual way to compare these algorithms.


The main focus is on correctness. There are many additional things we choose not to consider, not because we do not consider them important, but because they ultimately do not matter if the algorithm is correct. The first
of these is considering performance. We do not do a performance overview of our implementations. In fact, such a check would not be very useful at this stage, because many of our implementations do not attempt to have the best
performance, for example, we often choose to stick to base algorithm, rather than including performance optimisations. Our model-checker also considers a simple model of the algorithms, which does not include
certain additional features, such as undo or rich-text.


We feel the main benefit of this paper is the collection of implementations and property-checkers we provide. We encourage others to add algorithms and properties to this collection, and we hope that this approach will make
work on collaborative text-editing more easily accessible, and will help future work to avoid the correctness problems that have appeared in the past.

\subsection{Properties}

The most basic requirement of an algorithm convergence. That is, every client reaches the same version of the document state after all messages in the network have been received. Convergence is not enough because it is important that the version of the document reached matches the intention of the user.
The weak list specification, strong list specification \cite{Attiya2016} and non-interleaving properties \cite{Weidner2025Fugue} attempt to formalise what `intention' means.

\subsection{CCI Model}

Early work on OT proposed the CCI model for collaborative text-editing algorithms. CCI stands for convergence, causality preservation, and intention preservation. Convergence says that all documents should reach
the same state once all network messages have been received. Causality preservation says that if $O_b$ causally depends on $O_a$ then $O_a$ must be executed before executing $O_b$. Intention preservation 
says that when executing an operation, the change must satisfy the original intention of the user.

The main flaw with the CCI model is that the definition of intention preservation is not formal. There is no way to formally check whether an algorithm satisfies intention preservation, so this model
is not useful to reason with. For this reason, we move away from this model and use Attiya et al's weak list and strong list specifications, which attempt to formalise `intention'.

\subsubsection{Weak and Strong List Specification}

Attiya et al \cite{Attiya2016} formalised the problem of collaborative text editing as the weak and strong list specification.

The main idea is that if a character $a$ appears before a character $b$ in some client's document states, $a$ must appear before $b$ in every client's document
state. The difference between weak and strong is that the weak list is more relaxed about the orderings of deleted characters. Satisfying the strong list specification
is not as important as satisfying the weak list specification.


We quote the relevant parts of these specifications here, but refer to the original paper
for the full properties.

They model three kind of events that a client (or server) can perform in an algorithm:

\begin{enumerate}
  \item
    $do(op, w)$ - The operation $op$ is executed locally, and the document state after is $w$. The two kinds of operations we consider
    are $ins(i, x)$ (insert character $x$ at position $i$) and $del(i, x)$ (delete character $x$ at position $i$).
  \item
    $send(m)$ - The client sends the message $m$.
  \item
    $receive(m)$ - The client receives the message $m$.
\end{enumerate}


An algorithm satisfies the strong list specification if there exists a relation $lo$ satisfying the properties:

For all events $e=do(op, w)$ where $w = a_0 \dots a_{n-1}$:
\begin{enumerate}
  \item
    \begin{enumerate}
      \item
        $w$ contains exactly the elements visible to $e$ that have been inserted, but not deleted.


      \item
        The order of the elements is consistent with the list order.
      \item
        Elements are inserted at the specified position.
    \end{enumerate}
  \item
    $lo$ is transitive, irreflexive and total.
\end{enumerate}



The weak list specification only changes condition 2. 









\subsubsection{Interleaving}

One limitation of the weak and strong list specifications is that they allow for interleaving behaviour. When the users insert text concurrently at the same position, some algorithms may interleave those changes
within one another, rather than display the changes separately. This issue was noticed, but not properly formalised until the forward non-interleaving and maximal non-interleaving, which restrict the algorithm to only give non-interleaving
orders.

Weidner and Kleppmann \cite{Weidner2025Fugue} formalised the non-interleaving properties. These properties define what it means
for an algorithm to not have the non-interleaving problem. 



The left origin of an inserted character is the character immediately before it at the time of insertion. If a character was inserted at
position $i$, then the character at position $i-1$ (in the state immediately after insertion) is its left origin. If $i=0$, then a special 
character $\mathit{start}$ is its left origin.

Similarly, the right origin is the character immediately after it at the time of insertion including tombstones, or a special character $end$. There is a subtlety here that
the right origin can be a deleted character because it includes tombstones. These properties are not clear for what the right origin is when there are no tombstones.

in the state that has $a$ as left origin, then $a$ must appear immediately before $b$ in the state.

\section{OT background}

This section gives an overview of the common terminology and properties used by OT algorithms.



OT algorithms have been typically expressed in two parts -- a control algorithm, and a set of transformation functions. The intent is that
the control algorithm makes certain assumptions about the properties of the transformation functions, and any functions that satisfy these properties
can be used with that algorithm.

\subsection{Inclusion Transformations}



For two operations $O_1$ and $O_2$ generated from the same state, we write $O_1' = IT(O_1, O_2)$ to mean that $O_1'$ is the transformed operation of $O_1$, now taking into account the effect of $O_2$.

There are two properties that have appeared in the literature for inclusion transformation functions. These are TP1 and TP2.


TP1 says that if $O_1' = IT(O_1, O_2)$ and $O_2' = IT(O_2, O_1)$, then $O_1' \circ O_2 = O_2' \circ O_1$. This ensures that when
two clients use $IT$, they will both reach the same state.


TP2 applies when there are three or more clients. $IT(IT(O_3, O_1), O_2') = IT(IT(O_3, O_2), O_1')$ where $O_1'$ and $O_2'$ are as before.



Finding transformation functions which satisfy TP2 has been a challenge. There are many that claim to satisfy TP2 in the literature, but many are shown to not
work, or are unchecked. One alternative to finding TP2-satisfying transformation functions is for the control algorithms that do not require TP2 -- these are sometimes called TP2-avoiding algorithms. 

\subsection{Exclusion Transformations}


Some algorithms propose the idea of an exclusion transform, which essentially intends to be the inverse of $IT$.

For two sequential operations $O_1$ and $O_2$, we write $O_2' = ET(O_2, O_1)$ means that $O_2'$ is the transformation of $O_2$ with the effect
of $O_1$ removed.

The reversibility requirement states that $ET$ acts as the inverse of $IT$. That is, $ET(IT(O_1, O_2), O_2) = O_1$ and $IT(ET(O_1, O_2), O_2) = O_1$.


For context, the reason $ET$ is used in algorithms is to reorder operation buffers. Suppose executing $O_1$ then $O_2$ takes a document from
state $S$ to state $S'$. Then $ET$ can be used to give a pair $O_1'$ and $O_2'$ such that executing $O_2'$ then $O_1'$ also takes a document from $S$ to $S'$. This is
done by calculating $O_2' = ET(O_2, O_1)$ the $O_1' = IT(O_1, O_2')$.  This ability to swap can be used to re-order any sequence of operations into any permutation.


Reversibility is a less common requirement than TP1 and TP2, but similar to TP2, we find transformation functions that incorrectly claim this property.



Note that inclusion/exclusion transformations have also been called forward/backward transposition, but these concepts are equivalent.

There is no published model-checker for these properties, so this implementation is the first. This section gives an overview
of the components and functionality of the checker.

\subsection{Checking for convergence}

To check for convergence, the model-checker receives all incoming messages in the network. It then checks that all document states are
equal.

\subsection{Checking for the strong list specification}

For each local insertion or deletion operation generated by the checker, the model-checker records the client's document state after it performed that local operation. Also, whenever the client receives
a message, the model-checker records what operation(s) were in that message. 



The model-checker checks condition 1a by maintaining a set of characters. The set is initially empty. The model-checker
iterates through each local operation generated by the checker. If it was an insertion operation, the character inserted is added to the set.
If it was a deletion operation, the deleted character is removed from the set. This set provides the set of characters that are visible in the state,
so the model-checker ensures that the state of the client matches up with this set at each point.

The model-checker checks condition 1c for each insertion operation generated by the checker. It simply checks whether the state afterwards contains the relevant character
in the correct position.


Conditions 1b and condition 2 are more difficult to check. The specification states there exists a $\mathit{lo}$ relation, but does not say what it is. Either the checker
needs to construct this relation, or it needs to prove that it cannot exist. The strategy is to work backwards from the conditions to find what the relation must be, and if
there is a contradiction, then that can be used to say that the strong list specification cannot be satisfied.

The relation is represented as a set of pairs of characters. This set is initially empty. Working backwards from
condition 1b, the checker adds every pair of a characters $(a,b)$ to this set where $a$ and $b$ are characters such that
$a$ appears before $b$ in some document state. Condition 2 states this relation must be transitive, and this is enforce by applying
the transitive closure to this set. Condition 2 states this relation must be irreflexive, and this can be checked by iterating through the list,
and checking there are no pairs of the form $(a,a)$. If there are, this is the contradiction to say that the strong list specification is not satisfied.

The only remaining part of condition 2 says that the relation must be a total relation. An irreflexive, transitive and total relation can always be constructed
from an irreflexive and transitive one by just arbitrarily adding edges to make the relation total without introducing a cycle. Therefore, if the model-checker
has found an irreflexive and transitive relation, then it can say that the strong list specification is satisfied.


To summarise, the model-checker:

Iterates through every state in every client after every operation. For every character $a$ that appears before another
character $b$, adds the pair $(a,b)$ to the list order. Apply the transitive closure to the list order. Check for irreflexivity.
If the list order is irreflexive, this execution satisfies the strong list specification, otherwise, it does not.


\subsection{Checking for the weak list specification}

This is similar to checking for the strong list specification, with the difference being in condition 2. The transitive closure
should now only be applied on the subsets $\{a \mid a \in w \}$ for each document state $w$. Everything else works the same.

\subsection{Checking for forward non-interleaving}


For each local insertion operation, the model-checker records the left origin of that character by recording the character
immediately before it at the point in which it was inserted. The forward non-interleaving condition can then by simply checked by iterating
over every pair of characters $a,b$. If $a$ is the left origin of $b$, $b$ appears earlier than any other element that
has $a$ as left origin, but $a$ and $b$ are not consecutive elements, then this means forward non-interleaving is not satisfied.
If this does not occur for all pair, then forward non-interleaving is satisfied.

\subsection{Checking for maximal non-interleaving}

The check for maximal non-interleaving is analagous to the checks for forward non-interleaving. These are straightforward iterations over
all pairs of characters, ensuring the relevant conditions are satisfied.



\subsection{Checking properties of transformation functions}


OT literature commonly suggests that the two parts of an OT algorithms -- the control algorithm and the transformation functions -- can be considered individually as two separate layers of the algorithm. This would
suggest verifying the properties of transformation functions on their own rather than with a control algorithm. We choose to push away from this because we feel that the two components
cannot be separated as cleanly as previous work suggests. Two transformation functions can both satisfy TP1 and TP2, yet lead to different behaviour when tested against the same
control algorithm. Furthermore, OT papers often give control algorithms, but do not give concrete transformation functions. When an OT algorithm is shown to not work, the issue has often
lied with the transformation functions.  Transformation functions should be considered as a key part of the algorithm, not merely as an implementation detail, or an application-specific concern.

\section{Algorithm implementations}

\subsection{dOPT}

The dOPT algorithm is the original OT algorithm. It is well known not to work because of an issue known in literature as the dOPT puzzle. When two clients become
more than two operations out of sync, the algorithm does not handle this case correctly. 

The Jupiter and adOPTed algorithms fix the issues with the dOPT problem. 

The Jupiter algorithm uses a server. The implementation was model-checked with transformation functions that were formally verified to work.  

The adOPTed algorithm is decentralised. It requires the transformation functions to satisfy TP2. The paper provides transformation functions, but these were later shown to fail to satisfy
TP2, and we are able to reproduce those violations in our implementation.


\subsection{SOCT2}

The SOCT2 is an OT algorithm that requires TP2 satisfying transformation functions. The functions in that paper claim to satisfy TP2, but actually
do not. The algorithm works with the TTF functions, which do satisfy TP2. The SOCT2 algorithm and GOTO algorithm were published independently, but seem
to be the exact same idea. SOCT2 requires the transformation functions to satisfy TP1, TP2 and the reversibility requirements. Note that the transformation functions
given in the paper do not work -- they do not even satisfy TP1. The algorithm can be made to work using the tombstone transformation functions.


SOCT3 is a similar algorithm to SOCT2, with the main change being that the delivery of operations is now serialised by introducing a sequencer (which essentially requires a server). This means that SOCT3 drops
the requirement for the transformation functions to satisfy TP2. This means SOCT3 claims to work with transformation functions that satisfy TP1 and the reversibility requirements,
but not TP2. No transformation functions satisfy this specific combination, so we test it with the original SOCT2 transformation functions (which do not work), and also the tombstone
transformation functions (which do work).


SOCT4 drops further the reversibility requirements, so we found it works with transformation functions that only satisfy TP1. It is important to note that SOCT4 makes a very
strong assumption that all clients are online, which is not made by SOCT2 and SOCT3.



\subsection{GOT}

The GOT algorithm claims to be a TP2-avoiding algorithm that does not use a server. We find this algorithm is entirely broken, failing to converge. On top of this, the transformation functions
given in the paper do not satisfy the reversibility requirements they claim to satisfy. We provide an example of this.
We tried to implement the algorithm using TTF, and was able to achieve convergence, but still not achieve the weak list specification.




\subsection{WOOT}

We found the WOOT algorithm satisfies convergence and the weak and strong list specification. WOOT does have issues with performance, so it may be more
useful to use one of its predecessors.

\subsection{Assumptions made by each algorithm}

%% Assumptions made about the server / network 
%% Assumptions made about the transformation functions (TP1 or TP2)



One reason it has been difficult to compare the algorithms fairly is that their assumptions about the network are often very different. Some algorithms make stronger
assumptions about the network, and ignoring these assumptions can lead to making misleading claims.

The first kind of assumption is about the existence of a server. This is not necessarily bad, but the server can act as a point of failure. Previous work has made the
distinction between a transformation-based server and a non-transformation-based server. We feel this is not a useful distinction as any algorithm with a transformation-based
server can easily be made into one with a non-transformation-based server by having the server only be used to serialise the operations, and the clients can simulate the 
work of the server.

The second, strictly worse assumption is that the algorithms assumes all clients are online. If one client crashes, the whole algorithm stops and no more messages are delivered until 
all clients are back online. Now instead of having a single point of failure, the algorithm has many points of failure. It is better to use an algorithm that has a server than an
algorithm that makes this strict assumption, even if it does not have a server.

Some algorithms have not been explicit about which of these assumptions are satisfied. Algorithms, such as COT, POT and TIBOT have been listed as not requiring a server, even though they do. The most common example are the TP2-avoiding algorithms. One approach for these is to 
ensure that every client receives the operations in the same order. This is known as total order broadcast, and implementing that often involves making one of these assumptions. That is,
either by introducing a server, or making the system no longer fault-tolerant (for example, by waiting until a message is received from all clients). Note there is a third option to use a fault-tolerant consensus
algorithm, such as the RAFT algorithm. Previous work has incorrectly conflated causal-order broadcast with total-order broadcast. Causal order broadcast is much simpler to 
implement asynchronously; it is most commonly done in these algorithms using vector clocks.
