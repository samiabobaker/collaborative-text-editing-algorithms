\section{Introduction}

Collaborative text-editing algorithms allow multiple users to edit the same text document concurrently; they are used in popular software such as Google Docs and Overleaf. In the field
of collaborative text-editing algorithms, there is an over-arching issue of correctness. There are many published algorithms, and many open source implementations, yet
it is not very well-studied the correctness properties of many of these algorithms. In fact, there are algorithms shown after publication to simply not work \cite{Oster2005Proving}. A lot of these algorithms come without proof of their correctness properties, and some
come with incorrect hand-written proofs \cite{Oster2005Proving}. Many algorithms pre-date the correctness properties, with no one going back to check whether or not the algorithm satisfies it. To add to these issues, there are many algorithms with no publically available implementation. This has led to claims based on algorithms for which no one has
externally verified their correctness. To help combat these issues, we provide three things: a model-checker designed for the task of testing correctness properties
of collaborative text-editing algorithms; a collection of implementations of all major algorithms in research and open-source; and a set of results on the correctness properties
and issues we found with all the algorithms we implement. These should act as a guide for other attempting to implement these algorithms, without wanting to search through results through many decades of
academic papers. We hope these mean that similar correctness issues are avoided in future work, and for others to add to this collection
with future algorithms and properties. 


Our model-checker uses randomised testing to test a very large number of states in an algorithm. We check whether these states satisfy known properties 
of collaborative text-editing algorithms: convergence, weak list specification, strong list specification \cite{Attiya2016}, forward non-interleaving and maximal non-interleaving \cite{Weidner2025Fugue}.
An alternative would have been to write a formal mechanised proof of the algorithms. This has the advantage that it provides certainty of the algorithm's correctness
compared to our model checker, which can only check a finite number of cases. However, the benefit of using model-checking is that writing a proof is time-consuming
and easy to get wrong. There are examples of algorithms being proven correct, to later be found wrong \cite{Oster2005Proving}. Another benefit is that model-checking checks a real implementation rather
than an idealised model of the algorithm, which helps to spot both implementation bugs and bugs in the underlying algorithms. Our model-checker requires no
additional effort beyond implementing the algorithm.

Our collection of implementations aim to reduce the ambiguity in the descriptions of some of these algorithms. We find some papers give vague descriptions of
certain components of an algorithm. Some algorithms have many variants or interpretations in different papers, which go by the same name. Some algorithms have bugs with fixes in open-source implementations, but not clearly documented
anywhere. Some of these fixes also inadvertently lead to issues elsewhere. We aim to document these kinds of issues that we found to avoid confusions for others in the future. Our implementations focus on the correctness of the base algorithms, so we leave performance
optimisations and additional features (such as string-wise operations \cite{Lv2016}, undoing, moving \cite{Kleppmann2020} and rich-text \cite{Litt2022}) out of scope of our work. Similarly, we leave the use of these algorithms
for non-plain text documents (such as graphics editing \cite{Sun2002}, and XML \cite{Davis2002}) out of scope. We give some motivation for why we avoid some of these in future sections.


Our set of results appear in the form of a table of algorithms and their respective properties, which we find using our model-checker. This aims to collate
all the existing work on collaborative text-editing algorithms, to provide a clear place to see which algorithms satisfy which properties and which do not.


\autoref{sec:background} and \autoref{sec:otbackground} provide background of the relevant concepts we check for in our model-checker. These are the main concepts
require to understand our results and implementations, and provides the context and approach by which we approach this research. \autoref{sec:modelcheckerimplementation} gives a description of the implementation of our model-checker. To our knowledge, 
it is the first implementation of these properties, and we describe the features and issues of this model-checker. \autoref{sec:modelcheckerresults} gives the results of our model-checker,
showing which algorithms satisfy which properties. \autoref{sec:algorithmimplementations} describes the important things we found when implementing these algorithms, including counter-examples
to properties, ambiguities in the algorithm and known bugs. 



\section{Background} \label{sec:background}

This section provides background on collaborative text-editing algorithms, and on the properties of these algorithms that we check with our 
model-checker. 

\subsection{Introduction to collaborative text-editing algorithms}

The goal of a collaborative text-editing algorithms is to allow for users to edit a single text document concurrently in real-time. When a user makes a changes to the
document, network messages are sent so that every other user sees this change. We consider two types of changes: $\mathit{ins}(i, x)$ means that $x$ is inserted in the document at position $i$, $\mathit{del}(i)$ means that the character at position $i$ is deleted.

These algorithms must have a response user interface even if the network is slow. That means when a user makes a change, it should be applied instantly to the local document, without waiting for any other client in the network. This means, when a clients receives a message of another client's change, the state of their document may be very different from the document those changes were originally executed on. The main difficulty is ensuring this situation
is handled correctly in all scenarios.

There are two general approaches to solving this problem: operational transform (OT) and conflict-free replicated data types (CRDTs). We describe OT more in \autoref{sec:otbackground}. A CRDT is a data structure specially designed to handle changes being made concurrently. The operations are represented in a way such that they have the same effect regardless of the order they are executed.

Another way to categorise these algorithms is by the assumptions they make about the network. Some algorithms assume the existence of a server, and some are decentralised. Generally, the logic becomes simpler when there is a server, but it is a single point of failure, and not having a server may be preferred in many cases. Another assumption some algorithms make is that all clients are online, and the algorithm stops working if one client is disconnected from the rest of the network. This is a much worse assumption to make than assuming a server exists, since now every device is a point of failure. 

\subsection{CCI Model}

The CCI model \cite{Sun1996} was devised in early work on these algorithms to define what it means for an algorithm to be correct. The three properties it describes are convergence, causality-preservation and intention-preservation. Convergence means that all clients eventually reach the same document state, once all network messages have been received. Causality-preservation means that if 
an operation $O_b$ is causally dependent on $O_a$, then $O_a$ must be executed before $O_b$ on all clients. Intention-preservation says that when an operation is executed, the intention
of the user must be preserved. The CCI model is not formally checkable because the idea of `intention' is vague. In the context of text-editing, a more formally checkable set of properties are the
weak and strong list specifications \cite{Attiya2016}, so we use these in our model-checker.    

\subsubsection{Weak and Strong List Specification}


Convergence is not a strong enough requirement. The trivial way to achieve convergence is to have all clients always delete the entire document. The weak and strong list
specifications describe what must appear in the document, and in what order. The first main idea is that a character must appear in the document if and only if an insertion operation
of it has been seen, and a deletion operation has not been seen. The second is that if a character $a$ appears before a character $b$ in some client's document states, $a$ must appear before $b$ in every client's document
state. The difference between weak and strong is that the weak list is more relaxed about the orderings of deleted characters.


We quote the relevant parts of these specifications here, but refer to the original paper \cite{Attiya2016}
for the full properties.



\begin{property}[Strong List Specification]
  There exists a binary relation $lo$ on the characters of the state, called the list order, such that:
  \begin{enumerate}
    \item
      Each event $e = do(op, w)$ returns a sequence of elements $w = a_0 \dots a_{n-1}$, such that:
      \begin{enumerate}
        \item
          $w$ contains exactly the elements visible to $e$ that have been inserted, but not deleted.
        \item
          The order of these elements is consistent with the list order:
          $\forall i,j. (i < j) \implies (a_i, a_j) \in lo$.
        \item
          Elements are inserted at the specified position: if $op = ins(a, k)$, the $a = a_{min\{k, n-1\}}$.
      \end{enumerate}
    \item
      The list order $lo$ is transitive, irreflexive and total, and thus determines the order of all insert operations in the execution.
  \end{enumerate}
\end{property}


\begin{property}[Weak List Specification]
  There exists a binary relation $lo$ on the characters of the state, called the list order, such that:
  \begin{enumerate}
    \item
      Same as strong list specification.
    \item
      The list order $lo$ is irreflexive and, for all events $e = do(op, w)$, it is transitive and total on $\{a \mid a \in w \}$.
  \end{enumerate}
\end{property}

\subsubsection{Interleaving}

One limitation of the weak and strong list specifications is that they allow for interleaving behaviour. When the users insert text concurrently at the same position, some algorithms may interleave those changes
within one another, rather than display the changes separately. This issue was known, but not properly formalised until the forward non-interleaving and maximal non-interleaving properties \cite{Weidner2025Fugue}, which restrict the algorithm to only give non-interleaving
orders. There are two kinds of interleaving: forward and backward. Forward interleaving occurs when text is written in the forward direction (typing ``cat'' by typing
`c' then `a' then `t'). Backwards interleaving occurs when text is written in the backward direction (typing ``cat'' by typing `t' then `a' then `c'). Forward non-interleaving
attempts to disallow the forward interleaving case. There are cases when it is impossible to disallow both forward and backward interleaving, so maximal non-interleaving disallows 
allows both when possible, but prefers forward non-interleaving if disallowing both is not possible.

We quote the relevant properties below, but refer to the original paper for the full details.

\begin{definition}[Left Origin]
  The left origin of an element is the element directly preciding its insertion position at the time of insertion. If the element was inserted by 
  an $ins(i, x)$ call, then its left origin was at index $i-1$ at the time of this call. If $i=0$, then its left origin is a special symbol
  $\mathit{start}$
\end{definition}

\begin{definition}[Right Origin]
  The right origin of an element is the element directly following its insertion position at the time of insertion, in the list including tombstones. If the element was inserted by 
  an $ins(i, x)$ call, then its left origin was at index $i+1$ at the time of this call. If $i$ is the end of the list, then its right origin is a special symbol
  $\mathit{end}$
\end{definition}

\begin{property}[Forward non-interleaving]
  An algorithm is forward non-interleaving if it satisfies the strong list specification and the following holds for all list elements $A$ and $B$ in all possible list
  states: if $A$ is the left origin of $B$, and $B$ appears earlier in the list than any other element that has $A$ as left origin, then $A$ and $B$ are consecutive list
  elements.
\end{property}

\begin{property}[Maximal non-interleaving]
  An algorithm is maximal non-interleaving if it satisfies the strong list specification and the following holds for all list elements $A$ and $B$ in all possible states:
  \begin{enumerate}
    \item
      (Forward non-interleaving) If $A$ is the left origin of $B$, and $B$ appears earlier in the list than any other element that has $A$ as left origin, then $A$ and $B$ 
      are consecutive list elements.
    \item
      (Backward non-interleaving) If $B$ is right origin of $A$, and $A$ appears later in the list than any other element that has $B$ as right origin, then $A$ and $B$ are
      consecutive list elements. There is an exceptional case where this does not need to be true (see the original paper).
    \item
      If $A$ and $B$ have the same left origin and the same right origin, then the element with the lower ID appears earlier in the list.
  \end{enumerate}
\end{property}

\section{OT background} \label{sec:otbackground}

This section gives an overview of the common terminology and properties used by OT algorithms.

The idea of OT is to transform incoming remote operations with respect to local operations that have already been performed. For example, if a client receives an 
$del(3)$ operation, but it has performed $ins(2,x)$, then the original character has shifted one to the right so the deletion is now transformed to $del(4)$. The functions
which describe these transformations are called transformation functions. Transformations functions are paired with a control algorithm, which describes when and how to call these 
transformation functions.  The intent is that the control algorithm makes certain assumptions about the properties of the transformation functions, and any functions that satisfy these properties
can be used with that algorithm.

\subsection{Inclusion Transformations}


The first kind of transformation function is an inclusion transformation, which is what is used by all control algorithms. 

\begin{definition}[Inclusion Transformation]
  For two operations $O_1$ and $O_2$ generated from the same state, we write $O_1' = IT(O_1, O_2)$. $O_1'$ is the transformed operation
  of $O_1$, now taking into account the effects of $O_2$. For example, $del(4) = IT(del(3), ins(2, x))$.
\end{definition}

There are two properties that have appeared in the literature for inclusion transformation functions, which are often required for the control algorithms to converge. These are TP1 and TP2.

\begin{property}[TP1]
  If $O_1$ and $O_2$ are operations, and $O_1' = IT(O_1, O_2)$ and $O_2' = IT(O_2, O_1)$, then $IT$ satisfies TP1 if 
  $O_2' \circ O_1 = O_1' \circ O_2$. That is, for all document states, executing $O_1$ then $O_2'$ will always result in the same
  document state as executing $O_2$ then $O_1'$.
\end{property}

TP1 is the basic property that ensure that using $IT$ will lead the clients to converge. However, when there are more than two clients, it turns out this is not
enough. This leads to a second property TP2.

\begin{property}[TP2]
  If $O_1$ and $O_2$ are operations, and $O_1' = IT(O_1, O_2)$ and $O_2' = IT(O_2, O_1)$, then $IT$ satisfies TP2 if 
  for all operations $O$, $IT(IT(O, O_1), O_2') = IT(IT(O, O_2), O_1')$.
\end{property}

Finding transformation functions that satisfy TP2 has been a challenge. Previous work has shown that TP2 cannot be satisfied without introducing additional parameters into the operations \cite{Randolph2015}. Many functions claim to satisfy TP2, but were later shown to not \cite{Oster2005Proving} or are unchecked by others
\cite{Randolph2015, Sun2017}. It is important to note that, for many control algorithms, satisfying TP2 is not a requirement. TP2-avoiding algorithms are algorithms that 
are designed to avoid the issues that require TP2. With these algorithms, it is fine to use functions that do not satisfy TP2.

\subsection{Exclusion Transformations}


A few algorithms additionally use exclusion transformations, which are the inverse of $IT$.

\begin{definition}[Exclusion Transformations]
  For two operations $O_1$ and $O_2$ where $O_2$ is generated from the resulting state of $O_1$, we write $O_2' = ET(O_2, O_1)$. $O_2'$ is the transformed operation of $O_2$,
  now exluding the effects of $O_1$.
\end{definition}


Exclusion transformations must satisfy the reversibility requirement, which enforces that $ET$ and $IT$ are inverses.

\begin{property}[Reversibility Requirement]
  If $O_1$ and $O_2$ are operations, then:
  \begin{enumerate}
    \item $ET(IT(O_1, O_2), O_2) = O_1$
    \item $IT(ET(O_1, O_2), O_2) = O_1$
  \end{enumerate}
\end{property}


This only relevant to a few algorithms. Nonetheless, there are transformation functions which claim to satisfy the reversibility requirements, but actually do not (see \autoref{sec:gotimplementation}).
Note some papers use the terms forward and backward transpositions. These roughly correspond to inclusion and exclusion transformations.

\section{Model-checker implementation} \label{sec:modelcheckerimplementation}

In this section, we describe our implementation of the model-checker. To our knowledge, no published checker has been implemented for the strong and weak list specifications and for the non-interleaving properties, so this is the main contribution of our work.

\subsection{Interface between algorithms and model-checker}

We start by describing the interface between our algorithms and the model-checker, which determines the assumptions the model-checker has of the algorithms.
Our implementations represents algorithms using the \texttt{ClientDevice} and \texttt{ServerDevice} (if the algorithm uses a server) interfaces. The interfaces provide
some mechanisms for the model-checker to interact with the devices.

The first is the method \texttt{perform\_operation}, which allows the model-checker to execute a \texttt{ClientOperation} or \texttt{ServerOperation}. These operations
include local changes to the document (such as \texttt{ClientInsertOperation} and \texttt{ClientDeleteOperation}), and also receiving operations from other devices
(such as \texttt{ClientReceiveFromClientOperation}). By including receiving operations, the model-checker has control over the order in which messages are delivered to 
which device at which time, allowing it to model a wide range of network scenarios. Note that not all operations have to be relevant to all algorithms; for example, we include a \texttt{ClientTimestepOperation} only relevant to the TIBOT and TIBOT 2.0 algorithms.

One important point is that the local operations generated by the checker are only character-wise, not string-wise. 

Another point is that \texttt{perform\_operation} returns a list of operations seen by the client. This allows the model-checker to known what operations were actually received when a client receives a messages from another device.

A second mechanism are the methods \texttt{can\_receive\_from} and \texttt{can\_receive\_from\_server}. Algorithms tend to restrict the delivery order of operations. The most common way is to use a causal order, enforced by vector clocks. We give the choice of restriction to the algorithm and that is exposed to the model-checker through these methods that return what other devices a client can receive from.

Finally, there is the method \texttt{read\_state} which the model-checker can use to see the document state of the client. The state is represented by the type 
\texttt{list[UniqueChar]}. It is simply a list of unique characters. \texttt{UniqueChar} is just a character with a unique id attached to it, which we use because many 
of the algorithms and specifications assume every character is unique.

\subsection{Generating operations}

The model-checking generally follows the following steps. It first generates an operation to be executed on one of the clients or the server. It executes that operation, and records which operations were performed on which, what the states of the clients were after each operation and other useful information (for example, the left and right origins of each character). It repeats this with more operations to produce a trace of the execution. After the trace is fully generated, it is passed to one of the checkers which will decide whether or not the property being checked is satisfied.

The possible choices for an operation to be generated are an insertion or deletion at every position in the state, or receiving a message
from one of the other clients or server. We then can choose these operations at random, or check each one exhaustively up to a certain depth.
We implement both, but focus mainly on random generation.

\subsection{Checking for convergence}

Checking for convergence is very simple. The checker ensures that all network messages have been delivered by having each client/server receive operations
until there is nothing left to receive. The checker then checks that all the document states of the clients are equal, and reports a violation if not.

\subsection{Checking for the strong list specification}

The strong list specification checker takes in a trace containing the state of each client after each operation. It also contains what operations were visible
to each client at each point (which is determined by what is returned from \texttt{perform\_operation}). It can use this trace to check each condition.

Condition 1a is checked by maintaining an initially empty set of characters.For each client, the model-checker
iterates through each local operation generated by the checker. If it was an insertion operation, the inserted character is added to the set.
If it was a deletion operation, the deleted character is removed from the set. At each point, the checker tests whether this set is equal the set of characters in the client state. If not, it reports a strong list specification violation.

Condition 1c is checked only for states following a local insertion operation. The checker tests whether the character at the position of insertion is equal
to the inserted character, and reports a violation if not.

The other conditions use the list order $\mathit{lo}$. The specification says there exists a list order, but does not specify how to construct it. This makes it more
difficult to check, but what we do is backwards from the conditions to construct the list order satisfying them. Either the checker successfully constructs a list order, or it finds a contradiction showing that one cannot exist, and reports a strong list specification violation.

The list order is represented as a set of pairs of characters. It is initially empty. Working backwards from condition 1b, the checker adds every pair of a characters $(a,b)$ to this set where $a$ and $b$ are characters such that $a$ appears before $b$ in some document state. Working backwards from the requirement that $\mathit{lo}$ is transitive, the checker applies the transitive closure to the list order. For the requirement that $\mathit{lo}$ is irreflexive, this can be done by iterating through the set of pairs and checking there are no pairs of the form $(a,a)$. If there are this is the contradiction to say that a list order cannot exist satisfying these properties.

The only remaining part is that $\mathit{lo}$ must be a total relation. An irreflexive, transitive and total relation can always be constructed from an irreflexive and transitive one by arbitrarily adding pairs to make the relation total without breaking irreflexivity. Therefore, if the model-checker has found an irreflexive and transitive relation, then it can say an irreflexive, transitive and total list order must also exist, and the specification is satisfied.

Essentially, this is building a graph where the nodes are characters in the state and an edge from $a$ to $b$ means that $a$ appears before $b$ in some state. If this graph is acyclic, then the strong list specification is satisfied. If it contains a cycle, it is not satisfied.

\subsection{Checking for the weak list specification}

Checking for the weak list specification is mostly the same as checking for the strong list. Now the list order only has to be transitive on the subsets of characters
$\{a \mid a \in w \}$ for each $w$, where $w$ is the state of some client after a local operation. This translates to having to do the transitive closure, once for each
state and only on the characters in that state. As before, there is a single check for irreflexivity at the end.

\subsection{Issues with checking for non-interleaving}

The non-interleaving properties assume that the algorithms use tombstones, because the right origin may be a tombstone. We find this causes difficulties when the algorithm does not use tombstones, as the properties are not explicit in that case. It is not straightforward to add tombstones to an algorithm that does not use it, as the position of the tombstones is not well-defined. It may need to be considered further to what extent these properties can be tested
on those algorithms. We avoid these issues by considering insertion-only when checking for interleaving, leaving deletions for future work. The behaviour of deletions is still checked in the strong and weak list specifications, so we consider this an acceptable omission.

Another issue this avoids is that the properties use the list order from the strong list specification. It is difficult to construct this order in this scenario. When checking for the strong and weak list specifications, we constructed part of the list order, but left out the part enforcing that it was total. It was sufficient to say
the list order could be made total by adding arbitrary pair. That argument does not work here, because we actually need a specific instance of the list order. There are many choices to make when adding arbitrary pairs, and those choices will affect whether or not the order is interleaving. We avoid this issue by only considering insertions, since the order can be easily determined by the final document states after all clients converge.

\subsection{Checking for non-interleaving}

The trace used in the non-interleaving checkers is the same as that for the strong and weak list specifications, but now includes the left and right origins of each characters. This is straightforward to determine by simply checking the elements immediately before and after the character at the time of insertions. Since there are no deletions, it is not possible for the right origin to be a tombstone.

Knowing these, the condition for forward non-interleaving is easy to check. The checker loops over all pairs of characters $A$ and $B$. If $A$ is the left origin of $B$, and $B$ appears earlier in the list than all other characters for which $A$ is left origin, but $A$ and $B$ are not consecutive, then a forward non-interleaving
violation is reported.

For maximal non-interleaving, the condition for backward non-interleaving can be checked analagously. Maximal non-interleaving's third condition defines the ordering 
of characters with the same left and right origin. Mathematically, this was included to ensure a unique ordering. It mentions an ID but does not enforce what that ID is.  We leave the choice of this ID to the algorithm as the one piece of freedom it has on the ordering of characters. For that reason, we do not check condition 3
of maximal non-interleaving.  

\subsection{Checking properties of transformation functions}

One may suggest the need for a TP1 and TP2 checker of transformation functions. However, we push against considering transformation functions individually from the control algorithm. This is contrary to most OT literature, which often views the two as separate layers; control algorithm are a generic algorithm which can be used with many domain-specific transformation functions. For this reason, some papers will specify a control algorithm, and not give any transformation functions, leaving it as an implementation detail. When there is a bug in an OT algorithm, it is unclear whether the issue is in the transformation functions or the control algorithm.

This is based on the premise that, as long as the transformation functions satisfy certain properties, the control algorithm will work as expected. We find that the transformation functions cannot be separated from the control algorithm so cleanly. In \autoref{sec:tm11andrandolphfunctions}, we find two transformation functions that both satisfy TP1 and TP2 but give different properties when tested with a control algorithm. This would suggest that the transformation functions are equally important to deciding the behaviour of an algorithm. Therefore, in this specific context of text-editing, we feel it is better to only consider OT algorithms 
as a pair of control algorithm and transformation functions, rather than attempt to consider the two separately.

\subsection{Assumptions made by each algorithm}  \label{sec:assumptions}

%% Assumptions made about the server / network 
%% Assumptions made about the transformation functions (TP1 or TP2)



One reason it has been difficult to compare the algorithms fairly is that their assumptions about the network are often very different. Some algorithms make stronger
assumptions about the network, and ignoring these assumptions can lead to making misleading claims.

The first kind of assumption is about the existence of a server. This is not necessarily bad, but the server can act as a point of failure. Previous work has made the
distinction between a transformation-based server and a non-transformation-based server. We feel this is not a useful distinction as any algorithm with a transformation-based
server can easily be made into one with a non-transformation-based server by having the server only be used to serialise the operations, and the clients can simulate the 
work of the server.

The second, strictly worse assumption is that the algorithms assumes all clients are online. If one client crashes, the whole algorithm stops and no more messages are delivered until 
all clients are back online. Now instead of having a single point of failure, the algorithm has many points of failure. It is better to use an algorithm that has a server than an
algorithm that makes this strict assumption, even if it does not have a server.

Some algorithms have not been explicit about which of these assumptions are satisfied. Algorithms, such as COT, POT and TIBOT have been listed as not requiring a server, even though they do. The most common example are the TP2-avoiding algorithms. One approach for these is to 
ensure that every client receives the operations in the same order. This is known as total order broadcast, and implementing that often involves making one of these assumptions. That is,
either by introducing a server, or making the system no longer fault-tolerant (for example, by waiting until a message is received from all clients). Note there is a third option to use a fault-tolerant consensus
algorithm, such as the RAFT algorithm. Previous work has incorrectly conflated causal-order broadcast with total-order broadcast. Causal order broadcast is much simpler to 
implement asynchronously; it is most commonly done in these algorithms using vector clocks.

\section{Algorithm implementations} \label{sec:algorithmimplementations}

This sections explains some of the results and gives important points about some of the algorithms presented in \autoref{tab:algorithmproperties}.

\subsection{dOPT}

The dOPT algorithm is the original OT algorithm. It is well known not to work because of an issue known in literature as the dOPT puzzle. When two clients become
more than two operations out of sync, the algorithm does not handle this case correctly. 

The Jupiter and adOPTed algorithms fix the issues with the dOPT problem. 

The Jupiter algorithm uses a server. The implementation was model-checked with transformation functions that were formally verified to work.  

The adOPTed algorithm is decentralised. It requires the transformation functions to satisfy TP2. The paper provides transformation functions, but these were later shown to fail to satisfy
TP2, and we are able to reproduce those violations in our implementation.


\subsection{SOCT2}

The SOCT2 is an OT algorithm that requires TP2 satisfying transformation functions. The functions in that paper claim to satisfy TP2, but actually
do not. The algorithm works with the TTF functions, which do satisfy TP2. The SOCT2 algorithm and GOTO algorithm were published independently, but seem
to be the exact same idea. SOCT2 requires the transformation functions to satisfy TP1, TP2 and the reversibility requirements. Note that the transformation functions
given in the paper do not work -- they do not even satisfy TP1. The algorithm can be made to work using the tombstone transformation functions.


SOCT3 is a similar algorithm to SOCT2, with the main change being that the delivery of operations is now serialised by introducing a sequencer (which essentially requires a server). This means that SOCT3 drops
the requirement for the transformation functions to satisfy TP2. This means SOCT3 claims to work with transformation functions that satisfy TP1 and the reversibility requirements,
but not TP2. No transformation functions satisfy this specific combination, so we test it with the original SOCT2 transformation functions (which do not work), and also the tombstone
transformation functions (which do work).


SOCT4 drops further the reversibility requirements, so we found it works with transformation functions that only satisfy TP1. It is important to note that SOCT4 makes a very
strong assumption that all clients are online, which is not made by SOCT2 and SOCT3.



\subsection{GOT} \label{sec:gotimplementation}

The GOT algorithm claims to be a TP2-avoiding algorithm that does not use a server. We find this algorithm is entirely broken, failing to converge. On top of this, the transformation functions
given in the paper do not satisfy the reversibility requirements they claim to satisfy. We provide an example of this.
We tried to implement the algorithm using TTF, and was able to achieve convergence, but still not achieve the weak list specification.




\subsection{WOOT}

We found the WOOT algorithm satisfies convergence and the weak and strong list specification. WOOT does have issues with performance, so it may be more
useful to use one of its predecessors.


\subsection{TreeDoc}

We found that the TreeDoc algorithm satisfies the strong list specification. There is some ambiguity over what is meant by TreeDoc in the literature. The original paper
represents a document as a binary tree. Each node in the binary tree can have mini-nodes. Other papers represent TreeDoc as a tree that is not binary. A node can have many right
children and many left children. Depending on the interpretation, this can lead to something closer to the Fugue algorithm. The original paper also 
describes two kinds of ID schemes, which each have different ways of correctly handling deletions.


\subsection{SDT, ABT and LBT}

SDT, LBT and ABT are three algorithms proposed by . They claim to be TP2-avoiding, and do not use a server. SDT was shown not to work, but LBT and
ABT have not been tested. We found that LBT fails, and we give a counter-example. We found that ABT does work with the transformation functions in that paper.


\subsection{TIBOT}

TIBOT avoids the need for TP2 by ensuring operations are delivered in a total order, which means it is not fault-tolerant.


\subsection{LOGOOT}

We implemented the LOGOOT algorithm .   The original version of this algorithm is knwon to have a divergence bug. That bug was fixed in the description of
this algorithm when implementing LOGOOT. Although we could not find any more divergence bugs, the algorithm has a significant bug where it will get stuck in an 
infinite loop. We were able to reproduce this bug. Our implementation allows you to set the base of the ids. With a larger base, it becomes more difficult to reproduce the
infinite loop bugs, because it relies on two random numbers hitting the same values. To reproduce the bug, we had to reduce the base to make this case more likely. There are many attempted fixes
to this bug in open source implementations. Most lead to divergence, but the one that we could not reproduce any cases of divergence for was the Alchemy Book implementation. The paper is slightly ambiguous over how to insert at the beginning and end of the document. It mentions begin and end sentinels, but not their ids.
We use the ids for the begin and end sentinels from previous implementations. 


\subsection{POT}

We found the algorithm for POT works as expected. This algorithm is often listed as a decentralised algorithm that does not use a server. This is misleading. The algorithm 
requires operations to be delivered in a total order (that is consistent with the causal order), but does not describe how such an order is implemented. Often, this requires a server
or making a strong assumption about the clients.

\subsection{TIBOT 2.0}

TIBOT 2.0 is a modification of TIBOT, with the only difference being in how the algorithm handles receiving remote operations. The algorithm has the same issues as TIBOT of assuming all 
clients are online. TIBOT works with group operations (which is a sequence of operations generated in the same time interval by the same client), but the TIBOT 2.0 description (while still
claiming to retain this characteristic of using group operations) assumes that the received operation is a single operation. The way to handle this is already described in the original TIBOT
paper (what it calls the SLOT algorithm), so we adapt the description to work with group operations in our implementation.

\subsection{COT}

Similarly to POT, COT is a TP2-avoiding algorithm that has been claimed to work without a server, but actually requires some total ordering mechanism on the operations,
The paper mentions that context can be represented either as a set of operations or as a vector clock. This is merely an implementation detail we use
vector clocks. There are re-descriptions of this algorithm in later papers, but these do not fully describe the transform method in the algorithm, which is only
fully described in the original paper. Although we do not consider performance, the paper notes that COT uses a very slow recursive algorithm -- too slow to model-check through even only a few hundred cases. 
Memoising the recursive algorithm (as mentioned in the paper) was therefore necessary for us to model-check it (and necessary in any practical implementation).

\subsection{LogootSplit}

LogootSplit is based on Logoot, and comes in three variants -- LogootSplitNaive, LogootSplitString, and LogootSplitAVL. These are just changes in the data 
structure, which only change performance, not the actual algorithm. We implement LogootSplitNaive. We find it satisfies the same properties as Logoot. We
could not find any instance of the infinite loop bug that was present in Logoot.

\subsection{Partial persistent sequences (PPS)}

A PPS represents position ids using rational numbers. An insertion between two characters simply involves finding a rational number between the character before and after. This idea is mentioned in other papers, but is generally dismissed because would require infinite precision
for floating points. We find that the algorithm presented also has further issues in that it does not generate unique identifiers. If two users concurrently insert at the same position, there needs to be
a scheme to ensure both users do not use the same identifier, while maintaing the dense property of rational numbers. The papers propose two schemes (giving each client their own subrange, or appending the client id to the digits of the identifier), and our checker finds that both schemes still lead
to collisions, which lead to divergence. When clashes do not happen, we find the algorithm satisfies convergence, the weak and strong list specifications, and exhibits 
interleaving behaviours.

\subsection{TM1.1}

The TM1.1 functions claim to satisfy TP2. We were unable to find any convergence violations when testing these with adOPTed, so we do not dispute the claim they satisfy TP2. However, we find that these
functions do lead to weak and strong list specification violations. The issue occurs because the functions delete an extra character that no client intentionally deletes. This makes them not very practical.

\subsection{Randolph functions}

The Randolph functions are another set of functions that claim to satisfy TP2. They give a proof, but we could not find any other verification of this claim. Using the functions, we could not find any convergence or strong/weak list specification violations. Therefore, not only do
they seem to satisfy TP2; they seem to be more practical than the TM1.1 functions. Note that these functions implicitly assuming a total ordering of the characters, and we simply achieve this by adding the client id and a per-client counter to
each character.

\subsection{Interleaving in OT algorithms}

Many OT algorithms only exhibit interleaving in one direction but not the other. Switch the ordering of the priority scheme switches which
direction of interleaving occurs. Such algorithms cannot satisfy maximal non-interleaving, but choosing the right direction of priority can mean the
algorithm only exhibits backward interleaving, therefore satisfying forward non-interleaving.
