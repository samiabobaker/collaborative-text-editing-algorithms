# Notation

The following notation is used throughout this chapter:

|                     |                                                                                                                                                               |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| $Ins(str, idx)$     | An operation that inserts the string $str$ at index $idx$.                                                                                                    |
| $Del(n(str), idx)$  | An operation that deletes $n$ characters (corresponding to $str$) from index $idx$.                                                                           |
| $P(O)$              | The insertion/deletion position index of operation $O$.                                                                                                       |
| $L(O)$              | The length of the insertion/deletion sequence of operation $O$.                                                                                               |
| $IT_{DI}(O_a, O_b)$ | An inclusion of the effect of $O_b$ on $O_a$, where $O_a$ is a $Del$ operation and $O_b$ is a $Ins$ operation. The resulting operation is denoted as $O^b_a$. |

# 2.1 Generic Operational Transformation (GOT)

The GOT algorithm [44] was among the earliest of TP2-avoiding OT algorithms. Its
transformation functions need not satisfy TP2, but instead must satisfy a reversibility
requirement (discussed in Section 2.1.4). In this section, we introduce key concepts and
then describe GOT's control algorithm.

**Vector Clocks.** Using timestamps to order events in distributed systems is unreliable
due to factors such as clock drift. GOT therefore uses vector clocks to capture the
causality between edit operations. Each user maintains a state vector whose length equals
the number of participating users, and the $i$-th element represents the number of
operations applied from user $i$. Every operation is also associated with a copy of the
originating user's state vector at the point the operation is generated[^1].

[^1]:
    In GOT, an operation's state vector reflects the originating user's state vector
    after the operation is applied. For example, if users A and B have user IDs 0 and 1
    respectively, and A generates its first operation $O_a$ before receiving any remote
    operations, then $SV_{O_a} = [1, 0]$. In Jupiter and adOPTed, an operation's state vector
    reflects the user's state vector before the operation is applied, so $SV_{O_a} = [0, 0]$.

**Remote Operation: Causally Preceding or Concurrent.** Each user maintains a history
buffer containing the sequence of operations the user has executed. For each operation in
the user's history buffer, the operation may either (1) causally precede or (2) be
concurrent to an incoming remote operation. An operation $O_a$, generated by user $k$, is
said to causally precede an operation $O_b$ (denoted as $O_a \rightarrow O_b$) if
$SV_{O_a}[k] \leq SV_{O_b}[k]$, where $SV_O$ denotes the state vector associated with
operation $O$. Concretely, if $O_a \rightarrow O_b$, it means that the user who generated
$O_b$ had already applied $O_a$ before generating $O_b$, and thus the effects of $O_a$ are
inherently incorporated into $O_b$. Operation $O_a$ is said to be concurrent to $O_b$
(denoted as $O_a \parallel O_b$) if neither $O_a \rightarrow O_b$ or
$O_b \rightarrow O_a$. If $O_a \parallel O_b$, it means that $O_a$ was generated in a state
where $O_b$ had not been applied (and vice-versa).

## 2.1.1 Causality Preservation

Causality preservation is enforced through the following rules. Let $N$ denote the total
number of users, identified by user IDs $0, \ldots, N-1$, and let $SV_{U_i}$ denote user
$i$'s state vector. A remote operation $O_{new}$ generated by user $i$ can be applied to
user $j$'s document state only if both of the following conditions hold:

1. $SV_{O_{new}}[i] = SV_{U_j}[i] + 1$, i.e. $O_{new}$ is the next immediate operation
   from user $i$ that user $j$ has not yet applied.
2. For every user ID $k \in \{0, \ldots, N-1\}$ with $k \neq j$,
   $SV_{U_j}[k] \geq SV_{O_{new}}[k]$, i.e. user $j$ has already applied all operations
   from other users that $O_{new}$ causally depends on.

If both conditions are satisfied, $O_{new}$ is causally-ready for execution; otherwise,
$O_{new}$ must be buffered until all missing dependent operations have arrived and been
applied.

## 2.1.2 Total Ordering of Operations

GOT avoids the requirement of TP1/2 by enforcing a total order of operation execution
across all users [43]. An operation $O_a$ generated by user $i$ is said to be totally
ordered before an operation $O_b$ generated by user $j$ (denoted $O_a \prec O_b$) if
either (1) $\sum SV_{O_a} < \sum SV_{O_b}$, or (2) $\sum SV_{O_a} = \sum SV_{O_b}$ and
$ID_i < ID_j$, where $\sum SV_O$ denotes the sum of all entries in $SV_O$. As we see
later, this total ordering requirement means that a user may need to undo and subsequently
redo already executed operations.

## 2.1.3 Transformations and the Context of an Operation

GOT uses two types of transformation functions: the Inclusion Transformation ($IT$) and
the Exclusion Transformation ($ET$). Both $IT(O_a, O_b)$ and $ET(O_a, O_b)$ produce a new
operation, $O'_a$, which is a transformation of $O_a$ to include/exclude the effect of
$O_b$. The precondition for applying $IT(O_a, O_b)$ is that the context of $O_a$ must be
equivalent to the context of $O_b$. The context of an operation $O$, denoted as $CT_O$,
refers to the sequence of operations that must be applied from the initial document state
to reach the document state that $O$ is defined upon—this concept is important because the
insertion or deletion index of an operation inherently reflects the cumulative effect of
all preceding operations. If this precondition is not satisfied, it means that either
$O_a$ already includes the effect of operations not in the context of $O_b$, or
vice-versa. In such cases, the inclusion of $O_b$ onto $O_a$ leads to incorrect
behaviour—the well-known dOPT puzzle arises from transforming two non-context-equivalent
operations [31]. Similarly, the precondition for applying $ET(O_a, O_b)$ is that $O_b$
must context-precede $O_a$; that is, $CT_{O_a} = CT_{O_b} + [O_b]$.

The context of an operation can be adjusted through inclusion/exclusion transformations.
In particular, for $IT(O_a, O_b) = O'_a$, the context of the resulting operation is
$CT_{O'_a} = CT_{O_a} + [O_b]$, and for $ET(O_a, O_b) = O'_a$, $CT_{O'_a} = CT_{O_b}$.

## 2.1.4 Control Algorithm and the Undo/Do/Redo Scheme

The GOT control algorithm is centred around the Undo/Do/Redo scheme. Viewing the user's
history buffer as a stack of executed operations, with the latest operation at the top,
when a remote operation $O_{new}$ arrives, the user undoes operations from the history
buffer until the topmost operation is totally-ordered-before $O_{new}$. $O_{new}$ is then
transformed as per the control algorithm, applied to the document state, and pushed onto
the history buffer. All undone operations are then sequentially included against $O_{new}$
and reapplied.

**An Incoming Operation.** When a causally-ready (see Section 2.1.1) remote operation
$O_{new}$ arrives at user $i$, and all $n$ operations in $i$'s history buffer—denoted as
$HB[0:n]$, i.e. the sequence of executed operations from index 0 to $n-1$ (excluding index
$n$)—are totally ordered before $O_{new}$, three cases arise when transforming $O_{new}$:

**Case 1.** All operations in $HB$ causally precede $O_{new}$, meaning $O_{new}$ can be
applied directly without any transformation. This case applies to all locally generated
operations.

**Case 2.** All operations in $HB[0:m]$ (or no operations if $m = 0$) causally precede
$O_{new}$, but all subsequent operations in $HB[m:n]$ are concurrent to $O_{new}$.

- Given that $O_{new}$ is causally-ready for execution at user $i$'s document, and all
  $O \in HB[0:m]$ causally-precede $O_{new}$, $HB[m]$ must be context-equivalent to
  $O_{new}$.
- Therefore, $O_{new}$ can be included against each operation in $HB[m:n]$ sequentially by
  performing $IT(IT(IT(\ldots), HB[n-2]), HB[n-1])$, abbreviated as
  $LIT(O_{new}, HB[m:n])$, where $LIT$ denotes a list inclusion transformation.

**Case 3.** All operations in $HB[0:m]$ causally precede $O_{new}$, but subsequent
operations in $HB[m:n]$ contain a mix of causally preceding and concurrent operations to
$O_{new}$. Let $EOL$ denote the list of causally preceding operations in $HB[m:n]$.

- Since $O_{new}$ is causally ready to be applied, $CT_{O_{new}}$ will contain only the
  operations in $HB[0:m]$ followed by operations in $EOL$. However, operations in
  $CT_{O_{new}}[m:]$ may not have identical insertion/deletion indexes to those in $EOL$.
  This is because $HB[m:]$ contains concurrent operations not part of[^2] $EOL$, meaning we
  need to construct a corrected list, $EOL'$, that exactly matches $CT_{O_{new}}[m:]$.
- $EOL'$ is constructed by adjusting each $EOL[i]$ to exclude the effect of preceding
  operations from $HB$, and then including the effects of preceding operations in $EOL'$.
  Formally, $EOL'[i] = LIT(LET(EOL[i], HB[m:i]^{-1}), EOL'[0:i])$, where $HB^{-1}$ denotes
  $HB$ in reversed order.
- The effect of all operations in $EOL'$ can then be excluded from $O_{new}$, since each
  $EOL'[i]$ context-precedes $EOL'[i+1]$, and $EOL'[-1]$ context-precedes $O_{new}$. The
  resulting operation is context-equivalent with $HB[m]$, and can therefore be included
  against $HB[m:n]$ to obtain the transformed operation.

[^2]:
    If $EOL[i]$ corresponds to $HB[m+j]$ where $j > i$, then $EOL[i]$ incorporates the
    effects of $j-i$ concurrent operations while the corresponding operation in
    $CT_{O_{new}}[m:]$ does not.

The paper introducing GOT [44] also defines transformation functions for text editing,
corresponding to the combinations of $O_a$ and $O_b$ being either $Ins$ or $Del$
operations. Sun et al. [44] state that any set of transformation functions may be used
with the GOT control algorithm, provided they satisfy the reversibility requirement: if
$O_a$ and $O_b$ are context-equivalent, then $ET(IT(O_a, O_b), O_b)$ must return $O_a$;
and if $O_b$ context-precedes $O_a$, then $IT(ET(O_a, O_b), O_b)$ must return $O_a$. In
Chapter 4, we show that this requirement is not met by the transformation functions
provided in the same paper [44].

# 3.1.2 Relative Addressing

An $Ins$ or $Del$ operation may become relatively addressed to an $Ins$ operation in an
exclusion transformation. For $ET_{II}(O_b, O_a) = O'_b$, if
$P(O_a) < P(O_b) < P(O_a) + L(O_a)$, i.e., if $P(O_b)$ falls within the range inserted by
$O_a$, then excluding $O_a$ from $O_b$ results in an undefined insertion index. This is
because $O_b$'s position depends on the effect of $O_a$, which is not present in
$CT_{O'_b}$ as $O'_b$ excludes the effect of $O_a$. $O'_b$ is therefore relatively
addressed to the base operation $O_a$, and $P(O'_b)$ is set to $P(O_b) - P(O_a)$, i.e.,
the offset of $P(O_b)$ from $P(O_a)$. During the transformation, $Save\_RA(O'_b, O_a)$ is
invoked.

**Excluding/Including a Relatively Addressed Operation.** A relatively addressed operation
cannot be excluded against any operation. It can only be included against its base
operation. This is enforced by (1) the control algorithm only ever invoking $LET$ and
$LIT$ functions (even when transforming against one operation), and (2) modifying $LET$
and $LIT$ to handle relatively addressed operations differently:

- $LET(O, OL)$ (where $OL$ denotes a list of operations) first checks if $O$ is relatively
  addressed by invoking $Check\_RA(O)$. If so, $LET$ returns $O$, skipping the
  transformation against $OL$.
- If $O$ is relatively addressed, $LIT(O, OL)$ checks whether $OL[0]$ matches the base
  operation stored in $O$ by invoking $Check\_BO(O, OL[0])$. If it does, $O$ is converted
  into an absolutely addressed operation through $Convert\_AA(O, OL[0])$, and the result is
  transformed against the remaining operations in $OL$. Otherwise, the inclusion against
  $OL[0]$ is skipped, and $LIT(O, OL[1:])$ is recursively returned.

We therefore need a way to determine whether two operations are merely different
transformed versions of one another and not two completely different operations.
Fortunately, we can use the state vector of the operation—each distinct operation will
have a unique state vector, but all transformed forms of an operation will share the same
state vector. As such, we implement $Check\_BO(O_{relative}, O_{base})$ to return True if
the state vector of the operation in $O_{relative}$'s `relative_addressed_to` field is
equal to $SV_{O_{base}}$.

Finally, for $Convert\_AA$, recall that the index of a relatively addressed operation is
offset from the index of its base operation. Therefore, we define
$Convert\_AA(O_{relative}, O_{base})$ to return a new operation with index
$P(O_{base}) + P(O_{relative})$, and its `relative_addressed_to` field set to None since
the resulting operation is now absolutely addressed.

# 4.1 Character Reordering and Divergence in GOT

We identified two significant issues with GOT when implemented with the transformation
functions presented in the same paper [44]. The first is of character reordering
(Section 4.1.1), previously discovered by Weidner and Kleppmann [55]. The second is of
divergence (Section 4.1.2). To our knowledge, divergence in GOT has not been previously
discovered. These findings mean that GOT fails to satisfy even the weak variant of the
list specification. The issues are presented through example executions with minimal
numbers of operations and clients required for reproduction.

## 4.1.1 Character Reordering

| User A ($ID_A = 0$)                          | User B ($ID_B = 1$)                           |
| -------------------------------------------- | --------------------------------------------- |
| $O_1 = Ins(x, 0)$, $SV_{O_1} = [1, 0]$ → `x` | $O_2 = Ins(b, 0)$, $SV_{O_2} = [0, 1]$ → `b`  |
| Apply Remote Operation $O_2$ → `xb`          | $O_3 = Ins(a, 0)$, $SV_{O_3} = [0, 2]$ → `ab` |
| Apply Remote Operation $O_3$ → `xba`         | Apply Remote Operation $O_1$ → `xba`          |

**Figure 4.1:** Users A and B both start from an empty initial state. A generates $O_1$
and B generates $O_2$, followed by $O_3$. A and B then apply each other's operations.
Intermediate states after applying each operation are shown on the left/right sides.

Consider the scenario illustrated in Figure 4.1. We focus on the execution of $O_1$ at B.
The total order of operations is $O_1 \prec O_2 \prec O_3$, so when $O_1$ arrives, B must
undo both $O_2$ and $O_3$. $O_1$ is then trivially applied without any transformation. To
redo $O_2$, the effect of $O_1$ is included onto $O_2$ to obtain $O^1_2$:

$$
\begin{aligned}
LIT(O_2, [O_1]) &= IT_{II}(Ins(b, 0), Ins(x, 0)) \\
&= Ins(b, 1) = O^1_2 && \text{(4.1)}
\end{aligned}
$$

As per GOT's undo/do/redo scheme, $O_3$ is redone in two steps. First, the effect of $O_2$
is excluded from $O_3$ to obtain $O'_3$:

$$
\begin{aligned}
LET(O_3, [O_2]) &= ET_{II}(Ins(a, 0), Ins(b, 0)) \\
&= Ins(a, 0) = O'_3 && \text{(4.2)}
\end{aligned}
$$

Then, the effects of both $O_1$ and $O^1_2$ are sequentially included on $O'_3$ to obtain
$O'^{1,2}_3$:

$$
\begin{aligned}
LIT(O'_3, [O_1, O^1_2]) &= IT_{II}(IT_{II}(Ins(a, 0), Ins(x, 0)), Ins(b, 1)) \\
&= IT_{II}(Ins(a, 1), Ins(b, 1)) && \text{(4.3)} \\
&= Ins(a, 2) = O'^{1,2}_3 && \text{(4.4)}
\end{aligned}
$$

After applying the redone operations $O^1_2$ and $O'^{1,2}_3$, B's document now reads
`xba`, meaning that integrating the remote operation $O_1$ leads to B's prior insertions
of $a$ and $b$ being reordered. The issue arises because $IT_{II}(Ins(a, 1), Ins(b, 1))$
(Equation 4.4) returns $Ins(a, 2)$, when it should instead return $Ins(a, 1)$. This is
because B generated $O_3 = Ins(a, 0)$ after generating and applying $O_2 = Ins(b, 0)$,
meaning that the insertion of $a$ at index 0 was made with the knowledge that $b$ was
already present at index 0 and with the intent to insert before $b$. Therefore, including
the effect of $O^1_2$ onto $O'^1_3$ should not result in $O'^{1,2}_3$ being shifted to the
right.

The insertions of $b$ at index 0 followed by $a$ at the same index is a backward insertion
scenario, which can occur in text editing when a user inserts a string, moves their cursor
to the start of that string, and then inserts another string. In such cases, the
transformation functions provided in the paper for excluding/including $Ins$ operations do
not meet the reversibility requirement. For the example illustrated in Figure 4.1, we
have:

$$
\begin{aligned}
IT_{II}(ET_{II}(O_3, O_2), O_2) &= IT_{II}(ET_{II}(Ins(a, 0), Ins(b, 0)), Ins(b, 0)) \\
&= IT_{II}(Ins(a, 0), Ins(b, 0)) && \text{(4.5)} \\
&= Ins(a, 1) \neq O_3 && \text{(4.6)}
\end{aligned}
$$

**Applying $O_2$ and $O_3$ to A.** A also reaches the state `xba` after applying $O_2$ and
$O_3$, so although both A and B converge to the same state, the state violates B's
original intent. We omit the step-by-step derivation for A here as it is presented in the
next subsection which explores an extension of this scenario wherein both clients diverge.

## 4.1.2 Divergence

In the extended scenario illustrated in Figure 4.2, User B additionally performs
$O_4 = Del(1(a), 0)$ after $O_3$.

| User A ($ID_A = 0$)                          | User B ($ID_B = 1$)                             |
| -------------------------------------------- | ----------------------------------------------- |
| $O_1 = Ins(x, 0)$, $SV_{O_1} = [1, 0]$ → `x` | $O_2 = Ins(b, 0)$, $SV_{O_2} = [0, 1]$ → `b`    |
| Apply Remote Operation $O_2$ → `xb`          | $O_3 = Ins(a, 0)$, $SV_{O_3} = [0, 2]$ → `ab`   |
| Apply Remote Operation $O_3$ → `xba`         | $O_4 = Del(1(a), 0)$, $SV_{O_4} = [0, 3]$ → `b` |
| Apply Remote Operation $O_4$ → `xa`          | Apply Remote Operation $O_1$ → `xb`             |

**Figure 4.2**

We first outline the steps A takes to integrate $O_2$, $O_3$, and $O_4$. $O_2$ is
concurrent to all operations in $HB_A$, so $O_2$ is integrated by applying:

$$
\begin{aligned}
LIT(O_2, [O_1]) &= IT_{II}(Ins(b, 0), Ins(x, 0)) \\
&= Ins(b, 1) = O^1_2 && \text{(4.7)}
\end{aligned}
$$

A's document now reads `xb`, and $HB_A = [O_1, O^1_2]$. When $O_3$ arrives,
$HB_A[0] = O_1$ is concurrent to $O_3$, but $HB_A[1] = O^1_2$ causally-precedes $O_3$, so
$EOL = [O^1_2]$, and $EOL'[0]$ is derived by excluding the effect of $O_1$ from $O^1_2$:

$$
\begin{aligned}
LET(O^1_2, [O_1]) &= ET_{II}(Ins(b, 1), Ins(x, 0)) \\
&= Ins(b, 0) = EOL'[0] && \text{(4.8)}
\end{aligned}
$$

The effect of $EOL'^{-1}$ is then excluded from $O_3$ to obtain $O'_3$:

$$
\begin{aligned}
LET(O_3, EOL'^{-1}) &= ET_{II}(Ins(a, 0), Ins(b, 0)) \\
&= Ins(a, 0) = O'_3 && \text{(4.9)}
\end{aligned}
$$

Then, the effects of $O_1$ and $O^1_2$ are included on $O'_3$ to obtain $O'^{1,2}_3$:

$$
\begin{aligned}
LIT(O'_3, [O_1, O^1_2]) &= IT_{II}(IT_{II}(Ins(a, 0), Ins(x, 0)), Ins(b, 1)) \\
&= IT_{II}(Ins(a, 1), Ins(b, 1)) && \text{(4.10)} \\
&= Ins(a, 2) = O'^{1,2}_3 && \text{(4.11)}
\end{aligned}
$$

After applying $O'^{1,2}_3$, A's document reads `xba`, and
$HB_A = [O_1, O^1_2, O'^{1,2}_3]$. When $O_4$ arrives, $O_4$ is concurrent to $O_1$, but
both $O^1_2$ and $O'^{1,2}_3$ causally precede $O_4$. Therefore,
$EOL = [O^1_2, O'^{1,2}_3]$. First, $EOL'[0]$ is derived by excluding the effect of $O_1$
from $O^1_2$:

$$
\begin{aligned}
LET(O^1_2, [O_1]) &= ET_{II}(Ins(b, 1), Ins(x, 0)) \\
&= Ins(b, 0) = EOL'[0] && \text{(4.12)}
\end{aligned}
$$

$EOL'[1]$ is derived in two steps: the effects of $O^1_2$ and $O_1$ are excluded from
$O'^{1,2}_3$ to obtain $O''_3$, and then the effect of $EOL'[0]$ is included on $O''_3$:

$$
\begin{aligned}
LET(O'^{1,2}_3, [O^1_2, O_1]) &= ET_{II}(ET_{II}(Ins(a, 2), Ins(b, 1)), Ins(x, 0)) \\
&= ET_{II}(Ins(a, 1), Ins(x, 0)) && \text{(4.13)} \\
&= Ins(a, 0) = O''_3 && \text{(4.14)}
\end{aligned}
$$

$$
\begin{aligned}
LIT(O''_3, [EOL'[0]]) &= IT_{II}(Ins(a, 0), Ins(b, 0)) \\
&= Ins(a, 1) = EOL'[1] && \text{(4.15)}
\end{aligned}
$$

We have $EOL' = [Ins(b, 0), Ins(a, 1)]$. The effect of $EOL'^{-1}$ is then excluded from
$O_4$:

$$
\begin{aligned}
LET(O_4, EOL'^{-1}) &= ET_{DI}(ET_{DI}(Del(1(a), 0), Ins(a, 1)), Ins(b, 0)) \\
&= ET_{DI}(Del(1(a), 0), Ins(b, 0)) && \text{(4.16)} \\
&= Del(1(a), 0)^{RA} = O'_4 && \text{(4.17)}
\end{aligned}
$$

The result, $O'_4$, is relatively addressed to $EOL'[0] = Ins(b, 0)$. Therefore, when
performing $LIT(O'_4, [O_1, O^1_2, O'^{1,2}_3])$, the first operation, $O_1$, is skipped,
since it is not the base operation of $O'_4$. However, the next operation,
$O^1_2 = Ins(b, 1)$, is the base operation of $O'_4$, so
$Convert_{AA}(Del(1(a), 0)^{RA}, Ins(b, 1))$ is invoked, which returns $Del(1(a), 1)$
(Equation 4.18). The effect of $O'^{1,2}_3$ is then included onto the result:

$$
\begin{aligned}
LIT(O'_4, [O_1, O^1_2, O'^{1,2}_3]) &= LIT(O'_4, [O^1_2, O'^{1,2}_3]) && \text{(first inclusion skipped)} \\
&= IT_{DI}(IT_{DI}(Del(1(a), 0)^{RA}, Ins(b, 1)), Ins(a, 2)) \\
&= IT_{DI}(Convert_{AA}(Del(1(a), 0)^{RA}, Ins(b, 1)), Ins(a, 2)) \\
&= IT_{DI}(Del(1(a), 1), Ins(a, 2)) && \text{(4.18)} \\
&= Del(1(a), 1) = O'^{1,2,3}_4 && \text{(4.19)}
\end{aligned}
$$

The transformed result, $O'^{1,2,3}_4 = Del(1(a), 1)$, corresponds to a deletion at index

1. However, the current state of A is `xba`, where the character at index 1 is $b$.
   Executing $O'^{1,2,3}_4$ in this state results in the incorrect state `xa`, where $b$ is
   deleted rather than the intended[^3] character $a$, which is actually at index 2.

[^3]:
    The operation stores the character intended for deletion only so that the operation
    can be undone. The stored sequence is never used to influence the transformation.

**Integrating $O_1$ at B.** To integrate $O_1$ at B, all operations in $HB_B$ are first
undone, $O_1$ is trivially applied, and $O_2$ and $O_3$ are redone. Until this point, the
steps taken are identical to those in Section 4.1.1. To redo $O_4$, first, the effects of
both $O_3$ and $O_2$ are excluded from $O_4$:

$$
\begin{aligned}
LET(O_4, [O_3, O_2]) &= ET_{II}(ET_{II}(Del(1(a), 0), Ins(a, 0)), Ins(b, 0)) \\
&= ET_{II}(Del(1(a), 0)^{RA}, Ins(b, 0)) && \text{(4.20)} \\
&= Del(1(a), 0)^{RA} = O'_4 && \text{(4.21)}
\end{aligned}
$$

Now, the result, $O'_4$, is relatively addressed to $O_3$, so when subsequently including
the effects of $O_1$, $O^1_2$, and $O'^{1,2}_3$ onto $O'_4$, the first two inclusions are
skipped:

$$
\begin{aligned}
LIT(O'_4, [O_1, O^1_2, O'^{1,2}_3]) &= LIT(O'_4, [O'^{1,2}_3]) && \text{(first two inclusions skipped)} \\
&= IT_{DI}(Del(1(a), 0)^{RA}, Ins(a, 2)) \\
&= Convert_{AA}(Del(1(a), 0)^{RA}, Ins(a, 2)) \\
&= Del(1(a), 2) = O'^{1,2,3}_4 && \text{(4.22)}
\end{aligned}
$$

The redone operations are $O^1_2 = Ins(b, 1)$, $O'^{1,2}_3 = Ins(a, 2)$, and
$O^{1,2,3}_4 = Del(1(a), 2)$. When these operations are applied to B's document, the
resulting document reads `xb`. Although $O_1$ is correctly integrated at B, the result
diverges from A's document state of `xa`, despite both A and B having executed the same
set of operations. In particular, A reaches an incorrect result due to an incorrect
derivation of $EOL'$ when it integrates $O_4$. In Equation 4.15, A derives
$EOL' = [Ins(b, 0), Ins(a, 1)]$; however, $EOL'[1] = Ins(a, 1)$, does not match
$CT_{O_4}[1]$, where $CT_{O_4} = [Ins(b, 0), Ins(a, 0)]$. This error cascades into
Equation 4.17, where $O'_4$ should have instead been relatively addressed to
$EOL'[1] = Ins(a, 1)$, which would have then led to $O'^{1,2,4}_4 = Del(1(a), 2)$ being
derived.

## 4.1.3 Root Cause

The root cause of the issues described in Sections 4.1.1 and 4.1.2 lie in the reversibility
requirement not being met. In particular, the transformation function $IT_{II}$ is to
blame. Given two insertions $O_a$ and $O_b$, Sun et al. [44] define $IT_{II}(O_a, O_b)$ to
produce $O^b_a$ with insertion position $P(O^b_a)$, where:

1. If $P(O_a) < P(O_b)$, then $P(O^b_a) = P(O_a)$;
2. Otherwise, $P(O^b_a) = P(O_a) + L(O_b)$.

Consider $O_1 = Ins(b, 0)$ and $O_2 = Ins(a, 0)$, where $O_2$ is executed after $O_1$.
Since $O_1$ context-precedes $O_2$, the operations are not context-equivalent, so
$IT_{II}(O_1, O_2)$ is not directly applicable as the precondition is not met. However,
after transforming both into context-equivalent forms $O^i_1$ and $O^i_2$ through a series
of inclusions/exclusions, suppose we find that $P(O^i_1) = P(O^i_2)$—this is exactly what
happens in Equation 4.4 and Equation 4.15. Then, applying
$IT_{II}(O^i_2, O^i_1) = O^{i,1}_2$ yields $P(O^{i,1}_2) = P(O^i_2) + L(O^i_1)$,
effectively pushing the insertion of $O_2$ after $O_1$. This is caused by
$IT_{II}(O_a, O_b)$ setting $P(O^b_a) = P(O_a) + L(O_b)$ when $P(O_a) = P(O_b)$. However,
since $O_2$ was intended to be inserted before $O_1$, its insertion sequence should never
be pushed past that of $O_1$.
